# Inkling-2-Mini on one rented spot GPU, below the cheapest public price, by OpenRelay's method

**Status: CONFIRMED (claim-grade), 2026-11-22 12:00 UTC.** The result below is read from `results/claims.json` (published
Daytona spot prices; metered beside them). Every other number in this file comes from a screen run named next to it (180 s

## Result

**Inkling-2-Mini beats the cheapest market price on real text on two GPUs: B300 0.66x, RTX PRO 6000 0.83x. The PRO 6000
also beats it on OpenRelay's random-token client (0.77x), where the B300 only ties.**

Bar: PrimeIntellect on OpenRouter, $0.0008265 per OpenRelay agentic-mix request (9.5K in / 380 out). Method: OpenRelay's
(open-loop, p95 TTFT < 4 s, seeds 7 and 8, 300 s cells, the worst seed's ACHIEVED rate priced at Daytona's published spot
price). Conservative, monotonic figures: every rung up to the quoted rate passes on both seeds.

**Why random tokens hurt this config, and why they are not the workload.** The winning configs use DSpark, the speculative
draft head that ships in the checkpoint. On real text it accepts **3.02-3.03 tokens per verify step**; on OpenRelay's
random-token prompts only **1.55**, the same on all three DSpark boxes (server logs, split by the column-A and column-B time
windows; journal step 229). Real text therefore needs about half as many verify steps per output token (1/3.03 vs 1/1.55):
on the B300 TPOT near the knee is ~30 ms on real text and 91-101 ms on random tokens, so the random-token client sees a slower
server. Real traffic is text: random token ids have no structure for a
drafter to predict. OpenRelay's client therefore undersells models whose speed depends on speculation (the same effect the
GLM-5.3 work found). Both columns are shown on every price line; the claim is column B.

- **Why the PRO 6000's conservative figure leads.** Seed 7 FAILS the 1.35x rung on column B (p95 4.38 s) between two

**Caveat: this quality check can only rule out a large loss.** The vendor recipe against ITSELF (two runs, same box, same
config) differs at McNemar p = 0.02 and by 3 points on MMLU-Pro (76.5% vs 79.5%), because the model's "repetitive
reasoning" loops hit the 16K-token cap on a different 21-29 of the 200 MMLU-Pro questions each run (greedy decoding is not
batch-invariant in this engine). So MMLU-Pro differences of a few points here are run-to-run noise, not a serving effect,
and a small quality change would not be visible. DSpark and mixed-chunk stay inside the reference's own spread (20-31
truncations; GSM8K 96.4-97.2% vs 95.2-96.0%). Greedy texts
diverge early between configs (median first divergence ~140 characters; 67% identical between two runs of the same
config), answers agree 92-95%. Files: `raw/agree_*.json`.

## The model and the bar

- **Model:** `thinkingmachines/Inkling-2-Mini` @ `b85c3cfa615fc413cc9af3379f491b963f3b586a`, released 2026-11-20, Apache-2.0.
  - 26.4B total / 3.4B active MoE (8 of 128 experts).
  - A looped transformer: 24 layers, layers 6-17 run three times with shared weights, so 48 layer visits per token (5.4B
    effective active parameters).
  - 20 sliding-window (1024) and 4 full-attention layers, head_dim 128, relative-bias attention with gates and sinks, short
    convolutions, block attention residuals, a rank-64 gated controller between loop passes.
  - One ~20 GB checkpoint: NVFP4 experts in layers 0-19, MXFP8 experts in layers 20-23, everything else BF16.
  - A 3-layer DSpark draft head ships in the same checkpoint (`mtp.safetensors`).
  - Card and configs: `raw/hf_README_b85c3cf.md`, `raw/hf_config_b85c3cf.json`.
- **No full-precision original exists.** HF's launch blog calls NVFP4 + MXFP8 the model's native scheme. Thinking Machines
  published no BF16 Inkling-2-Mini; their other loop checkpoint (`TML-d24-varloop-research`) has the same format and
  different weights. The quality reference is therefore the official checkpoint on the vendor's recipe (below).
  Evidence: `raw/reference_check_20261122T071452Z.json`.
- **The bar:** OpenRelay does not list the model. OpenRouter's cheapest provider is PrimeIntellect (fp4): $0.075 / 1M input,
  $0.30 / 1M output, $0.015 cached (`research/raw/phase2_or_endpoints_thinkingmachines_inkling-2-mini_20261122T070046Z.json`).
  At OpenRelay's agentic mix (9.5K uncached in / 380 out) that is **$0.0008265 per request**. Io Net (nvfp4) is $0.08 / $0.35.
  Re-checked 2026-11-22 10:59 UTC: unchanged (`raw/or_endpoints_inkling-2-mini_20261122T105921Z.json`); OpenRelay's
  pricing page still does not list Inkling (`raw/openrelay_pricing_20261122T105928Z.html`, 0 matches).
- **Third-party references we could not run:** Cloudflare Workers AI serves only `inkling-2-small` (authenticated model
  search, 07:15 UTC); OpenRouter's PrimeIntellect and Io Net endpoints answer HTTP 402 with the only key on this machine
  (never purchased credits).

## The method (phase 1's, unchanged)

- OpenRelay's agentic mix: input uniform 1.9K-17.1K (mean 9.5K), output uniform 76-684 (mean 380), open-loop arrivals,
  `rate x 300` prompts per rate, 300 s cells, seeds 7 and 8, the worse seed kept, SLO p95 TTFT < 4 s.
- **Column A:** OpenRelay's own client (`vllm bench serve`, random-token prompts) plus their prefill probe.
- **Column B:** our real-text client (`bench/traffic.py`), tokenizer-exact, stratified lengths. **The price claim must hold on
  column B.** For Inkling, column B uses `--ttft-basis token`: the model's first chat token is a special token the reasoning
  parser emits no text for, so a text-only first-token clock would add one decode step.
- **Price:** the worst seed's ACHIEVED req/s at the highest rate that passes on both seeds, on Daytona's published spot price
  of the whole box (GPU + vCPU + RAM + disk). `analysis/` claims rules (`results/claims.json`).
- **Quality:** GSM8K test[:250] with OpenRelay's prompt and '####' scoring plus MMLU-Pro 200, greedy, reasoning effort "high"
  (0.9, the chat template's default), max_tokens 16384, on the claim config AND on the vendor recipe (run twice, to measure
  greedy run-to-run noise). Agreement: `tools/agree.py` (accuracy delta with an exact McNemar test, same answer, same text).

## Why MI355X is capped: emulated NVFP4 MoE + the controller kernel (step 222)

Torch profiler through SGLang's admin endpoint (`box/sgl_profile.py`), 4 x 10K tokens, 25.7K tok/s:

| Kernel | Share |
|---|---|
| `_grouped_dequant_gemm` (MoE: NVFP4 experts dequantized to BF16 on gfx950) | 26.7% |
| `_rel_extend_fwd` (relative-bias attention) | 19.2% |
| `_controller_mix` (the loop's rank-64 gated controller) | 12.0% |
| hipBLASLt BF16 projections + lm_head | 11.2% |
| `_swiglu_fake_quantize` (activation quantization, emulated) | 9.3% |
| `_sconv_prefill_kernel` (short convolutions) | 6.3% |
| `_attn_res_kernel` (attention residuals) | 3.5% |

NVFP4 emulation costs ~37% and the controller 12%: the MI355X levers are a native FP4 MoE path and a better controller
kernel, which is kernel engineering beyond this weekend. Tuning the BF16 projections (what AITER's tuner covers) cannot move
the knee by more than ~2%.
