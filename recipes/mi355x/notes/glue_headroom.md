# Glue headroom: Gemma 4 31B's non-GEMM kernels on one MI355X

Task (lead, 2026-11-22 ~10:1x UTC): the "glue" is ~23% of pure-prefill kernel time (`notes/profile_knee_or_recipe.md`):
- GELU(tanh)*up + MXFP4 quant 7.2%;
- RMSNorms 5.2%;
- q/k split + norm + RoPE 4.9%;
- FP4 activation quant 2.2%;
- KV-cache write 2.1%;
- q FP8 quant 1.5%.

Does aiter v0.1.30, or the image's aiter, have faster or fused kernels for it? Is there a different d512 prefill attention
kernel? Phase 2 is only for items worth >= 1.5% of a forward. Measured 2026-11-22 10:19-10:26 UTC (4:19-4:26 AM Central),
2 spot boxes, ~$0.45.

**Verdict.** **No item qualifies for Phase 2.**
- **Already near HBM bandwidth:** the engine's glue at prefill M is the sandwich norms at 4.9 TB/s and the FP4 activation
  quant at 5.6 TB/s. The q/k/v norm + RoPE and the KV-cache write run at ~3.4 TB/s.
- **Best aiter swap, ~0.5% of a forward at M = 6912-8192:** `fused_qkv_split_qk_norm_rope_cache` on the 50 sliding layers
  (Triton, already in the image) saves ~1.0 ms per 8192-token forward, against ~2.9 ms needed for 1.5%. Every other
  candidate is slower or ties.
- **d512 prefill attention:** aiter v0.1.30 has no new kernel for it.
- **GELU*up + quant:** v0.1.30's kernel is the image's, with OpenRelay's `scaleM_pad` change upstreamed.
- **Where the glue's remaining headroom is:** removing passes by fusing into the GEMM epilogue (`notes/gemm_headroom.md`
  section 6, item 1). Faster stand-alone glue kernels from aiter don't provide it.

## Method

`box/glue_headroom.py` (reuses `box/gemm_headroom.py`'s clock sampler, graph timing and JSONL rows), on OpenRelay's image
by digest (vLLM 0.30.0, aiter 0.1.21.post2), with no engine on the GPU. Config `tools/mkcfg_gemm.py GL1B`.
- **Engine path:** a `torch.compile` replica of vLLM 0.30's Gemma 4 code (`vllm/model_executor/models/gemma4.py`).
  - Attention prep: per-head `q_norm`/`k_norm` (weighted) and `v_norm` (weightless), then neox RoPE from
    `cos_sin_cache[positions]`. Sliding layers use default RoPE with theta 1e4. Global layers use Gemma 4's proportional
    RoPE: theta 1e6, 64 of 256 angle pairs, zero-padded, head_dim 512, K == V. Then vLLM's own
    `reshape_and_cache_flash` into an fp8 NHD paged cache.
  - Sandwich norms: `rms(x) * w1 + residual` (x the layer scalar on the second site), then `rms(.) * w2`, then
    `aiter.per_1x32_f4_quant_hip(shuffle=True)`, exactly as vLLM's `gemm_with_dynamic_quant` quantizes.
- **Compiled the way vLLM compiles:** only the token dim dynamic (`mark_dynamic`), plus vLLM's `combo_kernels` Inductor
  settings.
  - The first run (`results/mxGL1_glue/20261122T101921Z`) used `dynamic=True`. That also made the head and hidden dims
    symbolic, and the replica ran ~2x the knee profile's per-call times: 508 us/layer vs ~218 us. Its comparisons are void.
  - **Validation of the re-run** (`results/mxGL1b_glue/20261122T102332Z`): attention prep is 183 us/layer at M=6912 on
    sliding layers (221 us global). In-engine, the profile shows 140 + 20 + 58 = 218 us/layer averaged over both types at
    M ~ 6.9K. The sandwich sites are 57 us of norms; in-engine the two norm kernels take 63 and 81 us.
  - If anything the replica is a little faster than the engine, so the savings below are not overstated.
- **Timing:** the same graph-captured, event-timed loop as the GEMM work. Every candidate's outputs are checked against
  the engine replica on the same inputs: q (bf16), the fp8 K/V cache contents at the written slots, and the
  residual and FP4 bytes.

Notes on the candidates:
- **`rope_kv`:** aiter Triton `fused_qk_rope_reshape_and_cache`, which vLLM uses for `pass_config.fuse_rope_kvcache`.
  - It still needs Inductor for the norms. The RoPE + fp8 KV write kernel alone (151 us at M=8192, sliding) costs as much
    as the engine's whole norm + RoPE pass (157 us). Slower everywhere: 0.42-0.90x.
  - This is consistent with vLLM capping that fusion at `rope_kvcache_fusion_max_token_num = 256` (decode only), though
    it loses even there for Gemma 4.
- **`qkv_fused`:** aiter Triton `fused_qkv_split_qk_norm_rope_cache` (in the image's 0.1.21; v0.1.30 adds output
  buffers and mRoPE, not speed).
  - It takes Gemma's `1 + w` weights, so I passed `w - 1`. With `w` passed as-is its output was exactly 2x off (first run).
  - It has no `v_norm`, so V is normalized in place first (39 us at 8192).
  - Wins only on sliding layers at M >= 6912 (1.11x).
- **`hip_fused`:** aiter HIP `fused_qk_norm_rope_cache_pts_quant_shuffle`, vLLM's `fuse_qk_norm_rope_kvcache` kernel.
  Head dims 64/128/256 only, so not the d512 global layers. 1.07-1.09x at M >= 4096, with the same `v_norm` pre-pass.
- **`fused_rms_mxfp4_quant`:** the add + RMSNorm + MXFP4 path OpenRelay measured at 0-3%. Here it is 0.92-1.01x. Its
  Triton quant also rounds differently from the HIP quant the engine uses: only 83% of the FP4 bytes are identical, so it
  would change numerics as well.
- **v0.1.30 `fused_rmsnorm_add_rmsnorm`:** new; Gemma-style sandwich, inlined because the image lacks it. It equals the
  engine to fp32 rounding (99.3% of FP4 bytes identical) but is only 0.88-1.08x, and it cannot take the layer scalar on
  the second site.
- **q FP8 quant:** none of the fused ops emits an fp8 Q the unified-attention backend would accept, so it stays a
  separate kernel in every variant.
- **Not measured:** a GEMM that takes BF16 activations and quantizes in-kernel (aiter Triton `gemm_a16wfp4`). It would
  replace a ~20 us quant at M=8192 with a GEMM from the Triton FP4 family. That family measured 0.59-0.76x of the asm
  path (`notes/gemm_headroom.md` section 3), i.e. roughly +50 to +550 us per call at M=8192 (158-800 us GEMMs), so it
  cannot win at prefill M.

## The three questions

1. **Faster or fused aiter kernels for the glue?** Yes, several exist, but none is materially faster than what Inductor +
   vLLM already run. The best is `fused_qkv_split_qk_norm_rope_cache` on sliding layers at large M: ~1.0 ms per
   8192-token forward (~0.5%). Every norm/quant fusion is slower or ties.
2. **A different d512 prefill attention kernel in v0.1.30?** **No.**
   - `mha_v4` supports head dim 128 or 256 (`aiter/ops/mha_v4.py` `_check_head_dim`).
   - The FlyDSL fmha kernels target other tiles and head dims.
   - The only "512" in `aiter/ops/attention.py` is MLA's latent `v_head_dim` (DeepSeek-style decode).
   - The d512 path stays the Triton `unified_attention`, which the recipe session already tuned (journal 129-130).
3. **Phase 2:** not run. Nothing reaches 1.5% of a forward.

## Where the glue headroom actually is

The glue kernels already stream at 3.4-5.6 TB/s. Making them faster stand-alone tops out at shaving the ~3.4 TB/s ones
toward ~5 TB/s; that is the ~1 ms above. The real lever is removing the passes:
- **GELU*up + MXFP4 quant (7.2%)** is a separate read of the 705 MB gate_up output per call at M=8192. Fusing it into the
  gate_up GEMM epilogue is item 1 of `notes/gemm_headroom.md` section 6, ledger t021.
- **Norm -> quant -> GEMM:** the sandwich norm writes a bf16 tensor that the quant reads back. A single
  norm-add-norm-MXFP4 kernel with the HIP quant's exact rounding would save an estimated ~30 us/site at M=8192
  (176 MB of bf16 write + read at ~5 TB/s). That is ~3.6 ms per
  forward (~1.9%), but it is a kernel to write: no aiter kernel matches both the sandwich and the rounding.
