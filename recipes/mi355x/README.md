## The bar

The bar is OpenRelay's post "Gemma 4 Optimization with Agentic Kernel Engineering"
(https://openrelay.inc/blog/gemma-4-agentic-kernel-engineering, 2026-09-29) and their recipe
(github.com/OpenRelayInc/inference-recipes @6767b4d, `gemma-4-31b-mi355x/`, saved under `research/raw/openrelay_recipe/`).
- Setup: one MI355X, their tuned vLLM 0.30 ROCm image, AMD Quark MXFP4, Google's MTP drafter with 2 draft tokens.
- Published: **3.0 req/s per GPU at p95 TTFT < 4 s** ("3.25 borderline"), TPOT p50 22 ms, prefill 41.9K tok/s, GSM8K 98.8%.

**Their recipe on our boxes is already 3.25.** Their image by digest and their flags on a Daytona spot MI355X pass 3.25 req/s on
both seeds and fail 3.5:
- seed 7: 3.28 s at 3.25, 10.71 s at 3.5;
- seed 8: 2.55 s at 3.25, 9.23 s at 3.5;
- runs `s2_mi355x_or_recipe_seed7/20261122T043703Z` and `s2_mi355x_or_recipe_seed8/20261122T043705Z`, journal step 100.

So "beating" them here means **3.5 req/s on both seeds**, measured on the same harness against their recipe on the same boxes.

## The method (theirs, unchanged)

- **Client:** `vllm bench serve` on `/v1/completions`, random-token prompts, input 9.5K x U(0.2, 1.8) (1.9K to 17.1K), output 380 x
  U(0.2, 1.8) (76 to 684). Open-loop Poisson, `rate x 300` prompts per rate, seeds 7 and 8, the whole run counts. A rate counts only
  if both seeds have p95 TTFT < 4 s. `bench/protocol.py --client vllmbench`.
- **Prefill probe:** 16 concurrent x 64 prompts of 10K tokens, run twice; the second counts.
- **Gate:** GSM8K test[:250] with their prompt and '####' scoring, at least 96.5%. Screens used the first 100.
- **Sampling** is whatever the server defaults to. `vllm bench serve` no longer sends temperature 0, so Gemma 4's
  `generation_config.json` applies: temperature 1, top_k 64, top_p 0.95. That holds for both recipes.
- **Real text, side by side.** Their own script notes random tokens give "97-98% MTP acceptance, far above real text". So every MTP
  result is also reported with our real-text client (`bench/traffic.py`, column B: tokenizer-exact, stratified 9.5K/380 prompts).

Same image, same weights, same everything as OpenRelay's recipe except:

## Why these changes: the journey

Each row is one change, screened on seed 8 at 300 s per rate on one box, against the same-seed control. The journal steps
(100-1xx in `results/experiments.jsonl`, rendered in `docs/JOURNAL.md`) carry the run ids, diffs and evidence files.
p95 TTFT is in seconds, at 3.5 req/s, seed 8 unless noted (control: 9.23).

| Step | Change | p95 TTFT at 3.5 | Decision | Why |
|---|---|---|---|---|

## The profile that found the drafter waste

OpenRelay's method is to profile at the knee and chase the biggest slice. We used their scripts (copied unchanged to `box/`)
plus one of ours, `box/outside.py`, which attributes the kernels that run outside the target model's step windows. Notes:
`notes/profile_knee_or_recipe.md`. Runs: `mx1_or_profile/20261122T050154Z` and `mx7_prof_mtp3_seqs96/20261122T054335Z`.

- **Where the knee spends GPU time.** MXFP4 GEMMs ~50% (at about half the MXFP4 peak), attention ~33%, norms and quant ~10%,
  KV writes ~2%. Mixed steps are 100% busy, with no host gaps.
- **The drafter outside the target forward.** At 3.5 req/s with k=3, 8.1% of kernel time (7.5 ms per step) ran outside the target
  forward. A head_dim-512 *prefill-shaped* attention call of ~2.9 ms ran once per mixed step, together with the drafter's BF16
  GEMMs.
- **The cause.** vLLM 0.30's `AutoRegressiveSpeculator.propose` runs draft position 0 over every token the target scheduled,
  including the whole 6-8K-token prefill chunk, then keeps only `last_token_indices`. Gemma 4's MTP head is Q-only. It reads the
  target's KV cache and writes none (`Gemma4Speculator.advance_draft_positions` is False), so that work is discarded.
- **The fix.** `box/patch_draft_compact.py` runs that pass on one token per request in steps that contain a prefill, using the same
  position and seq_len rule as the Gemma 4 decode passes. The drafter only proposes and the target verifies every token.
  Acceptance is unchanged (3.55-3.59 tokens per verify step patched; 3.62 unpatched on step 110's box) and the quality gate passes
  (GSM8K test[:250] 245-247/250).
- **Token-level output identity, measured** (run `mxID_identity/20261122T075235Z`, `box/identity_probe.py`). One box served our recipe unpatched, then
  patched. Probe: temperature 0, ignore_eos, 256 tokens, 50 short GSM8K prompts plus 10 random-token prompts of 10K tokens (two
  prefill chunks each).
  - **Patched vs unpatched, concurrency 1: 60/60 sequences token-for-token identical.** This holds both for the first runs (fresh
    prefix cache) and for the second runs (cache hits).
  - **Control, the same server run twice:** 50/60. The 10 that differ are exactly the long prompts, whose second run reuses the
    FP8 prefix-cache KV instead of recomputing it.
  - **At concurrency 16, batch composition dominates.** Unpatched c1 vs unpatched c16 agrees on only 19/60. Patched vs unpatched
    at c16 (23/60) is inside that noise, so c16 cannot separate a patch effect.
  - Expected: at temperature 0 the target's greedy verification fixes the output whatever the drafts are. The probe confirms the
    patch leaves no state behind that changes the target's computation.
- **What the patch writes (checked in vLLM 0.30's source).** It overwrites `input_ids`, `positions`, `seq_lens` and
  `query_start_loc` in the drafter's own `InputBuffers`, which `DraftModelSpeculator.__init__` allocates separately from the
  target runner's. The unpatched decode passes rewrite those same buffers right after the first pass anyway. It also writes
  `slot_mappings` on the shared `BlockTables`. The unpatched decode passes overwrite that too, and the model runner recomputes it
  every step (`model_runner.py` prepare inputs). The target's next step reads none of the overwritten state.

## What did not work, or was not tried

- **vLLM 0.34:** a silent 43% prefill regression on this model (above); parity once fixed.
- **ATOM** (AMD): Gemma 4 31B support (ROCm/ATOM#546) was closed unmerged on 2026-10-09, so there is nothing to run.
- **SGLang instead of vLLM** (Maks's question; journal steps 123, 125-127). Spec off throughout, their client, seed 8, prefill
  probe.
  - SGLang 0.5.23 (ROCm 10 gfx950 image; the ROCm 7.2 image exceeds Daytona's 20 GB snapshot limit) **cannot load AMD's MXFP4
    checkpoint**. It fails first on a missing processor config, then, with Google's added, on
    `assert param_data.shape == loaded_weight.shape` in `load_merged_column_weight`: the same two failures OpenRelay reported
    for 0.5.20.
  - On RedHat's FP8-dynamic checkpoint, SGLang prefills **17.2K tok/s against vLLM's 29.3K on the same weights**. vLLM with AMD's
    MXFP4 checkpoint reaches 43.8K and passes 2.5 req/s; both FP8 runs fail 2.5 req/s.
- **RedHat EAGLE-3 / DFlash2 drafters:** not run. Both must prefill the prompt through their own BF16 layers (DFlash2 is a
  5-layer drafter). On a 96%-prefill mix that costs prefill capacity that Google's KV-sharing MTP head does not.
- **FP8 KV cache:** already in their recipe (`--kv-cache-dtype fp8`, 977K tokens of KV).
- **MXFP4 "all-linear" Quark checkpoint:** not built. Only `lm_head` is still BF16 (2.8 GB read per decode step, ~0.5 ms), and
  re-quantizing needs a calibration run and a fresh GSM8K gate. The upside is too small for the weekend.
- **Concurrency-adaptive draft length:** vLLM 0.30 has `num_speculative_tokens_per_batch_size`. Not tried: a fixed k=3 already
  beats k=2 and matches k=4 at the knee.

## Caveats

- **Box-to-box speed.** Daytona MI355X spot boxes hold different sustained GFX clocks under this load: 1940-2060 MHz median across
  20 boxes, from `tools/gpumon_amd.py` on each run's raw `amd-smi` log. Pure prefill tracks it (41.3K to 43.5K tok/s), and at the
  cliff that moves p95 TTFT by seconds. Hence the paired confirm: the same GPU serves both recipes.
- **Random tokens flatter MTP.** Acceptance per draft token is 0.86-0.90 on their random-token prompts against 0.6-0.7 on real
  text. Column B (real text) sits beside every number.
- **TPOT.** Their 22 ms is at 3.0 req/s. Near 3.5 req/s, TPOT p50 is 31-37 ms for ours and 44-46 ms for theirs.
- **Errors.** About 1 request in 1,000 fails on random-token prompts. vLLM logs "invalid prefix detokenization" for garbage
  outputs. It hits both recipes and stays under their 1% rule.
- **Spot evictions** are recorded in the ledger and the affected cell is re-run on a fresh box (one so far: `mx6_or_mtp3_seqs80`).
